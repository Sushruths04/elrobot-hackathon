# Web console and voice agent layer over normakit (v1)

A self-contained web/voice layer (`webapp/`) that puts a "Claude Code in a web" console over the existing normakit stack: FastAPI backend with REST + WebSocket, a dark HUD frontend in vanilla JS, browser-native voice (Web Speech STT/TTS, zero GPU), and a Claude tool-use chat loop that imports `src/normakit/agent.py` read-only rather than forking it. The change was built to satisfy a strict brief: add the interface layer without touching anything the team has already built. That constraint is honored - the entire diff is new files under `webapp/`, one new doc page, and a single appended CHANGELOG bullet. All 10 new tests pass with no hardware and no API key (verified locally: `10 passed in 1.16s`).

Watch for:
- **Speaker toggle is coupled to the mic (confirmed)** - `speak()`/`speakTool()` in `app.js` bail unless `micOn` is also true, so SPK alone never produces spoken replies.
- **Human-presence gate is an unauthenticated self-assertion (confirmed)** - any process that can reach the port can `POST /api/confirm-human` and open the 10-minute motion window. Fine on the default 127.0.0.1 bind; it is not an authorization mechanism.
- **Silent failure edges (confirmed)** - the WS receive loop swallows all non-disconnect exceptions, and a chat that exhausts its 25-turn cap ends with no event at all, so the UI can go quiet without explanation.
- **E-stop writes bypass the single-writer lock (likely)** - deliberate so e-stop never blocks, and the halt payload (hold current position) makes the worst case benign, but it is a second writer on the serial bus by design.

**Verdict**: APPROVED

## High-level view

The webapp is a pure overlay: it imports `SYSTEM`, `TOOLS`, `run_tool`, and `MODEL` from `src/normakit/agent.py` verbatim and drives the same tool-use loop the CLI agent runs, with each step mirrored as a JSON event for the WebSocket. No file under `src/`, `scripts/`, `server/`, or `docs/01..12` is touched; the only existing-file edit is one appended CHANGELOG bullet. Claude API is the only model anywhere in the layer and there is no fine-tuning path.

The safety story is layered and fail-closed. `Guard` in `core.py` stays the hard layer and is never bypassed - the webapp never imports a Backend or calls `send_goals`; every motion goes through `normakit.agent.run_tool`, which drives `Arm` skills. On top of that, `run.py` refuses `--backend station` without `--i-have-a-human` (exit 2, tested), and a `HumanGate` blocks motion tools in station mode until a human confirms presence, with a 10-minute window enforced per tool call. The gate's motion-tool set is a superset of every motion tool `agent.py` actually exposes, so nothing slips through unclassified.

The transport surface is small and localhost-bound by default: three REST endpoints for status/e-stop/confirm plus one WebSocket that pushes joint telemetry (0.5 s) and camera frames (0.7 s) and accepts chat, e-stop, and cancel messages. A single global agent lock allows one chat at a time, and a threading lock serializes all motion writes, mirroring the repo's one-writer-on-the-bus rule.

Voice is entirely browser-side: `SpeechRecognition` turns speech into chat text with interim words shown live and final transcripts auto-sent; `speechSynthesis` reads replies aloud. No audio leaves the browser and no speech model enters the repo, which is why the layer needs zero GPU. The documented Whisper/Piper upgrade path on the A100 is placeholders only, marked not implemented.

The main gaps are polish rather than structure: the SPK toggle is wired so it only works when MIC is also on, the human gate authenticates nothing, a few failure paths go silent, and the frontend/voice logic plus the WS chat dispatch path have no automated tests. None of these block a sim-first hackathon demo.

## Read-only reuse of normakit's agent loop

The design choice that makes this diff safe to review is that `agent_bridge.py` contains almost no agent logic of its own. It imports `SYSTEM`, `TOOLS`, `run_tool`, and `MODEL` from `src/normakit/agent.py` and re-runs the same loop the CLI runs; what it adds is an `on_event` callback that turns every step (tool_use, image, tool_result, final, error, cancelled) into a JSON-able dict for the WebSocket, plus the `HumanGate` check before motion tools. Reading `agent.py` directly confirms the reuse is verbatim - same tool schemas, same `run_tool` dispatch - so behavioral drift between the CLI agent and the web agent is structurally impossible unless someone later edits the shared file.

```
browser (vanilla JS, no build, no CDN)
   |  WS /ws: state 0.5 s, frames 0.7 s, agent events
   |  REST: /api/status, /api/estop, /api/release, /api/confirm-human
   v
FastAPI (webapp/app.py, :8920, binds 127.0.0.1)
   |-- agent_bridge.run_chat  -> Claude tool-use loop, one event per step
   |-- safety.HumanGate       -> 10-min presence window + single-writer lock
   v
normakit Arm/Guard (src/normakit, read-only import)
   v
sim (pybullet, default)  |  station (real arm via Station :8888)
```

One consequence of the reuse: `run_tool` returns image content blocks for `look` but JSON strings for every other tool, and the bridge has to handle both shapes - it does, emitting the JPEG as an `image` event. The `stop` tool maps to `arm.guard.estop()`, so even the agent's own stop path lands on the hard layer rather than on the gate.

## HumanGate over Guard: the station safety chain

Three layers, each verified against the code. The hard layer is untouched: `Guard.estop` latches and halts, `Guard.move` refuses while latched, and the webapp has no path to `Backend.send_goals` at all - it never imports a Backend class. The operator layer mirrors `scripts/run_policy.py`: `run.py --backend station` exits with code 2 and a stderr message unless `--i-have-a-human` is passed.

The convenience layer is `HumanGate`, and the important check is classification coverage. `agent.py` exposes exactly eight tools: `look`, `pick_cell`, `place_cell`, `reach_cell`, `gripper`, `home`, `arm_state`, `stop`. The gate's motion set covers all five that move anything and adds `reach_xyz`/`move_joints`/`calibrate_table` as headroom for future tools - supersets fail closed here, so there is no unclassified motion path. The window check runs per tool call, so a window that expires mid-task blocks the next motion tool while `look` and `arm_state` keep working: the arm freezes mid-task rather than finishing a stale authorization, which is the right failure direction.

Two soft spots, both about who can assert rather than what the gate does. First, `POST /api/confirm-human` is unauthenticated: any local process - or any network client if the server is ever started with `--host 0.0.0.0`, which the README's hosting section explicitly contemplates via SSH tunnel or proxy - can open the motion window. On the default 127.0.0.1 bind this matches the repo's existing trust model (the Station UI on :8889 is equally unauthenticated), but the gate should not be mistaken for authorization; it is a friction ritual. Second, e-stop deliberately does not hold the single-writer lock: `Guard.estop` calls `halt()` while a motion tool may be mid-`send_goals` under `gate.lock`. Since `halt` writes each joint's current position as its goal, an interleaved write stops the arm rather than misdirecting it, and blocking e-stop behind a motion in progress would be worse - but on the station serial bus it is, strictly, a second writer.

## WebSocket fan-out, the agent thread, and its silent edges

Chat runs on a daemon thread so blocking `Arm` calls never touch the event loop; a global lock enforces one agent at a time across all connections, and a `threading.Event` lets e-stop or an explicit cancel stop the agent at the next turn boundary - mid-motion, Guard's own clamps and step limits still apply. Station mode re-detects the front camera on every frame error because Station renumbers cameras on replug, a constraint carried over from the team's hardware experience; sim always serves the fixed `"table"` camera.

The edges are all in the failure paths. The receive loop catches a bare `Exception` and passes, so a genuinely broken handler kills telemetry silently; the browser's `rec.onerror` is likewise mute by design. More concretely user-visible: if `run_chat` exhausts its 25-turn cap without Claude producing a final text (a long pick task that keeps re-looking can plausibly do this), the loop ends, no `final` and no `error` event is emitted, and the transcript just stops - the reader cannot distinguish "done" from "gave up". These are one-line fixes; they matter because the demo narrative relies on the transcript telling the story.

## Browser voice: Web Speech STT/TTS and the mic-coupled speaker

`SpeechRecognition` streams interim words into the input box and auto-sends the final transcript; `speechSynthesis` speaks final replies and short tool summaries ("picking cell C4"). Nothing is uploaded, no speech model is added, and non-Chrome browsers degrade to typing with a hint.

The one real bug is the coupling: both `speak()` and `speakTool()` start with `if (!micOn || !ttsOn || ...)`, so the speaker only works while the mic is also live. The UI and README present MIC and SPK as independent toggles, and a presenter who wants typed input with spoken replies - a reasonable demo mode - gets silence. The fix is deleting one condition. Also note the auto-send on final transcript means a misrecognized phrase goes straight to the agent; in station mode the gate still stands between a bad phrase and motion, which is exactly what the gate is for.

## Tests: 10 green without hardware, and what they don't cover

Ran the suite locally: `10 passed in 1.16s`, no hardware, no `ANTHROPIC_API_KEY`. Coverage includes the endpoints, WS state+frame push, the tool-loop event stream (the emitted base64 decodes to a real JPEG), station refusal exit code, gate blocking (asserting joint norms never moved), and e-stop-during-chat surfacing Guard's refusal through the tool results. Station-mode behavior is exercised by putting a sim arm behind a station-mode gate.

Not tested: the WS chat dispatch itself (the threading, the one-agent-at-a-time lock, cancel), the gate window actually expiring (only the never-confirmed and confirmed states are exercised), anything in `static/` (the mic/SPK bug above would have been caught by even a trivial JS test), and live station hardware - the last is disclosed plainly in `docs/13` as "sim only so far".
