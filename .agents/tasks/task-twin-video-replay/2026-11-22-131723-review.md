# Digital-twin video replay of the teleop pick session, plus web console screenshot

The branch answers the user's two-part ask: "show me how the webapp looks" and "can we do the digital twin kind of thing from the videos we have, maybe in MuJoCo". Part one is `scripts/screenshot_webapp.sh` plus a committed headless-Chrome capture of the live web console on the sim backend. Part two is the substance: a new MuJoCo desk scene (the validated elrobot twin with the cup/bottle object layer swapped for the white cardboard tray and marker measured from real frame 0 through the calibrated homography) and `scripts/twin_replay.py`, which writes the recorded raw servo ticks into the twin's simulated ST3215 registers, steps physics per frame, and renders real-vs-twin side by side. All 1058 frames of the `20261121_205828_teleop_pick1` session replay; the stills, a 60 s mp4, a GIF, a camera-alignment overlay and a metrics JSON are committed under `docs/twin/` with a docs/14 report page. The only existing-file change is an additive optional `scene_xml` parameter and guarded optional bodies in `MujocoBackend`; I re-ran `scripts/selftest_sim.py` (ALL OK) and the webapp pytest suite (10 passed) on this branch. The reporting is honest to the point of stating, in the metrics file, the docs page and ISSUE-116, that the sim marker grasp fails while the real video succeeds.

Watch for: the twin never grasps the marker (recorded joints put the jaw tips ~40 mm above the table at the grasp; ISSUE-116), so the side-by-side video shows arm tracking, not a reproduced pick (confirmed in replay_metrics.json and the f0616 still). The physics step length comes from the `joints.jsonl` t column that ISSUE-118 itself says drifts +3.8 s over the clip — low impact, but inconsistent with the file's own "frame index, never t" rule (confirmed in `scripts/twin_replay.py`). No automated test exercises the new `scene_xml` path or the backend guards (confirmed — no test references them).

**Verdict**: APPROVED

## High-level view

The replay is a servo-physics replay, not a kinematic puppet show: recorded raw ticks are written into the twin's simulated servo registers and MuJoCo integrates the PID, command lag, quantisation and contacts, so the side-by-side exercises the same twin that `scripts/validate_twin.py` already validated. Video sync is by frame index (jsonl line i is video frame i); the drifting t column is used only for physics step length, which is where a minor inconsistency with ISSUE-118 creeps in.

`twin_desk_scene.xml` is `elrobot_scene.xml` with only the object layer swapped: cup, bottle and place target out, a measured white cardboard tray and marker in. Arm, table, both cameras, contact exclusions and the jaw-mimic equality constraints are untouched, so the calibrated parts of the twin carry over unchanged. A handful of cup/bottle mesh and material declarations survived the copy as dead weight.

The `MujocoBackend` edit is the right shape: an optional `scene_xml` constructor parameter, and the optional scene bodies (cup, bottle, place target) become guarded lookups whose setters raise a clear RuntimeError when the body is absent, instead of silently indexing qpos at a wrong offset. Default-scene behaviour is unchanged; both regression suites re-run green in this review.

The metrics and docs are the honest part of the deliverable: every headline number in docs/14 and the CHANGELOG traces to the committed `replay_metrics.json`, the failing sim grasp is reported rather than hidden, and the tape-line pixel gap is correctly attributed to a real-table vs texture mismatch (ISSUE-117) instead of being papered over as camera error.

Repository hygiene checks out: ~26 MB of artifacts committed deliberately (task state marks docs/twin artifacts as meant-to-be-committed), gitignored recordings and presentation videos stayed out, commits used explicit paths, and the team's uncommitted working-tree changes are untouched. The small nits: no test covers the new code paths, the screenshot script can capture the wrong server if its port is already taken, and the committed task.json still says `in_progress` with the verification block sitting uncommitted.

### Servo-physics replay through the validated twin

The design choice worth noting is what the replay is not: it does not set joint angles kinematically per frame. It re-drives the twin the way the real bus was driven — `_sync(REG_GOAL_POS, raw ticks)` per frame, with `REG_ACC`/`REG_GOAL_SPEED` primed once, exactly the `validate_twin.py` pattern — and lets the simulated ST3215 profile, command lag and contact physics produce the motion. That makes the artifacts a twin validation as much as a visualisation: the EE error label on each frame is the sim EE versus `Kin` FK of the commanded ticks, i.e. servo tracking plus model discrepancy, which is what docs/14 says it is.

```
joints.jsonl  line i ──> _sync(REG_GOAL_POS, ticks) ──> MuJoCo servo physics, step dt
front.mp4     frame i ─────────────┐                          │
                                   ▼                          ▼
                          compose(real | frame_rgb("front"))  →  stills / mp4 / gif
                                                          └─> ee_err, marker z → replay_metrics.json
```

Sync is by frame index: one seek to the window start, then sequential reads, so video frame i pairs with jsonl line i. I checked the pairing against the f0616 still — real jaw closing at the marker, twin jaw closing at the marker, same frame index — and it holds.

One inconsistency lives here. ISSUE-118 documents that the jsonl t column drifts (+3.8 s over the clip, dt mean 0.1286 s vs the video's 0.125 s) and says to sync by frame index, never t. The video path honours that, but the physics step length is `ts[i+1] - ts[i]` — the same drifting t column (confirmed, `scripts/twin_replay.py` replay loop). Impact is small: per-frame timing noise of ~3% on a 125 ms step, and no accumulation error in the comparison because each frame is scored against its own commanded FK. Still, stepping by the nominal 1/8 s would match the stated rule and remove the jitter from the servo sim. Related minor point: the mp4 frame rate is hardcoded `8` in the `VideoWriter` while the mp4 length cap is derived from `ts` — fine for this session, silently wrong for a recording at any other rate (confirmed).

### Object layer measured from the real frame

The tray and marker poses are not guessed: table-contact pixels picked on real frame 0 were projected through `calibration/table_mujoco_front.json` (pixel on the z=0 plane → robot xy), then iterated against the twin render to ~10 px. The feature file records an honest deviation from the plan — the real tray measured ~0.10 × 0.13 m, not the planned 0.12 × 0.20 — and the scene was sized to the real objects. The committed metrics file carries the measured poses for provenance, and the CLI exposes them as overridable defaults.

The scene itself keeps everything calibrated untouched and swaps only the object bodies: `white_tray` (five thin box geoms, open box, ~33 g) and `marker` (two capsules, red + silver, ~0.12 m, 15 mm dia) as free bodies, with contact exclusions and jaw-mimic equalities preserved. Confirmed dead weight from the copy: the `cup_wall_*` hull mesh declarations and the cup/bottle/coaster materials are still declared but no body references them. Harmless — MuJoCo loads unused assets without complaint — but deleting them would make the scene file honest about what it contains.

### MujocoBackend becomes scene-agnostic

The edit is minimal and in the right direction. `scene_xml` is optional and defaults to the previous constant. The optional bodies (black_cup, distractor_bottle/bottle_freejoint, place_target) are now looked up defensively: absent joints store `None` qpos offsets, and every accessor (`set_cup_pose`, `cup_pos`, `cup_upright_cos`, `set_bottle_pose`, `set_place_target`) raises a RuntimeError naming the missing body instead of writing qpos at a garbage index — fail-loud is exactly right for a scene mismatch, because a wrong-offset qpos write would corrupt the arm state silently. `ee_site`/`jaw_tip_site` stay required with an explicit error, which keeps the arm contract non-negotiable.

### The metrics are the honest part of the deliverable

Every number in docs/14 and the CHANGELOG traces to the committed `replay_metrics.json`: EE replay error mean 4.93 / rms 15.25 / p95 15.58 mm over all 1058 frames, tape-line alignment +14.6 / −43.2 px, marker max height 0.72 cm with `sim_grasp_succeeded: false`. The tape-line paragraph does real work — it separates camera error (intrinsics residual 0.39 px) from a real-table vs `table_tex.png` layout mismatch (ISSUE-117), which is the correct attribution and keeps a future reader from "fixing" the camera.

Two things a reviewer should read past the headlines. First, the grasp honesty: the sim marker is never lifted because the recorded joints put the jaw tips ~40 mm above the table at the grasp, while the real video grasps and trays the marker with those same joints (ISSUE-116, guessed as a wrist-pitch/calibration residual between `Kin` FK and the real arm, labelled as a guess). The side-by-side mp4 therefore shows arm tracking, not a reproduced pick — the docs say this plainly, which is what saves the deliverable from overselling. Second, the mean/rms gap (4.93 vs 15.25 mm with p95 at 15.58) means the error budget is dominated by a thin tail of large-error frames, most plausibly fast teleop swings where servo lag spikes (likely — the arithmetic is confirmed, the cause is inference; per-frame errors are not saved, so the tail cannot be attributed from the committed artifacts). Not a discrepancy, but "mean 4.93 mm" alone would flatter the twin.

### Committed artifacts and repo hygiene

The 26 MB under `docs/twin/` (mp4 13.7 MB, gif 7.2 MB, eight ~0.65 MB stills, overlays) is committed deliberately — the task state explicitly marks these artifacts as meant-to-be-committed, and the gitignored locations (`run/recordings/`, `presentation/videos/`) stayed out; I verified the ignore rules and the per-commit file lists, and the team's uncommitted changes (including their CHANGELOG bullet) are still uncommitted and untouched.

One bookkeeping nit: the committed `.agents/tasks/task-twin-video-replay/task.json` still says `"status": "in_progress"` even though all three features are `completed`, and the verification block recording the green regression run sits as an uncommitted working-tree modification (confirmed via `git diff HEAD`). Not a code problem, but the branch tells a slightly stale story about itself.

The screenshot script polls for HTTP 200 with a dead-child check inside the loop, then screenshots and kills only the PID it started. One edge (confirmed mechanism, low likelihood): if something else is already listening on `$PORT`, the first poll gets a 200 from the foreign server before the dead-child check runs, and the script will happily screenshot the wrong backend while reporting success. Checking `kill -0` before accepting the 200, or defaulting to a random free port, closes it.

### Test coverage

Not covered by anything automated (confirmed — no test file references `twin_desk_scene`, `twin_replay` or `scene_xml`): the new constructor parameter, the absent-body RuntimeError guards, and the replay script's window/GIF/metrics logic. The `MujocoBackend` guard paths in particular are the kind of code that rots silently — a ten-line smoke test (load `twin_desk_scene.xml`, assert `cup_pos()` raises, render one front frame) would lock in both the new capability and the backward-compat claim. The replay script itself is a pipeline whose verification is its artifacts, which is defensible; the backend change is library code and deserves the test.
