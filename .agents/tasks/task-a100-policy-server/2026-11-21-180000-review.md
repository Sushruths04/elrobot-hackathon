# A100 policy server and robot-side client (v1)

Adds a FastAPI server that hosts a LeRobot policy (ACT picked) on the A100, a shared pydantic schema, an HTTP client, and `scripts/run_policy.py`, which sends state and a camera frame to the server and feeds the returned action chunk into `Guard.move`. A model comparison and plan (`docs/10_MODEL_AND_A100_PLAN.md`) justifies ACT with SmolVLA as fallback. Only the dummy-policy path has run, on the sim backend. The real LeRobot 0.4.4 path, the Docker image and the real arm are untested, and no trained checkpoint exists yet.

Watch for: (1) chunk rows are 30 fps but are consumed one per 10 Hz tick, so a trained policy plays back about 3x slow and `chunk_dt` is ignored (confirmed); (2) `/act` is unauthenticated when `POLICY_API_TOKEN` is unset, the server binds `0.0.0.0` and speaks plain HTTP (confirmed); (3) the real-model path hardcodes one camera key and assumes policy outputs are already 0..1 joint norms (likely); (4) the dry-run test would pass with several of its checks broken (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The A100 only returns a chunk of 8-joint norm targets. The robot side owns the clock and sends every command through `Guard.move`.

The timing model does not match the plan. The docs say chunks are sub-sampled or interpolated to the 10 Hz Guard rate and fetched asynchronously. The code does neither: it takes one row per tick and fetches synchronously. With ACT trained at 30 fps this changes the speed of every learned motion.

The server's security is opt-in. Anyone who can reach port 8000 can drive the arm's targets unless the operator remembers to set a token, and the token travels in cleartext.

The real-model adapter makes several silent assumptions about the checkpoint (camera name, action units and dimension). The dummy test cannot catch any of them.

1. **Chunk playback rate** (confirmed) — `run_loop` sends one 30 fps row per 10 Hz tick and ignores `client.chunk_dt`. Resample the chunk by `chunk_dt * hz` (skip or interpolate) so playback is real time, or document and test the slowdown.

4. **Hardcoded camera key and units** (likely) — `observation.images.table` is fixed, and the postprocessed action is clamped to 0..1 on the assumption the dataset stored norms. Read the keys from `policy.config.input_features` and validate the action range at load.
5. **Silent action truncation** (likely) — `r[:N_JOINTS]` hides a checkpoint with more than 8 action dims, and fewer dims surface only as a client-side shape error. Assert the dimension at startup.
6. **Missing image gives a 500** (likely) — a vision policy called without `image_jpeg_b64` fails inside the preprocessor. Return a 422 when the policy needs an image.
7. **Weak dry-run test** (confirmed) — the health check `.get("status","ok") is not None` is always true, and the 0.02..0.98 check runs on Guard output, which is clamped by construction. Auth, the 401 path, chunk-rate behaviour and the real adapter are not tested. Assert on `ready`, send a bad token, and check playback speed.

## Chunk playback at 10 Hz versus 30 fps

`LeRobotPolicy.act` returns `1/fps` as `chunk_dt` (30 fps for the repo's dataset). `run_loop` never reads it. Each tick it takes `chunk[idx]`, moves toward it by at most `max_delta` (0.05), and increments `idx`. It refetches when `idx >= len(chunk)//2`. A 20-row chunk therefore covers 10 rows, which is 0.33 s of demonstrated motion, spread over 1 s of wall time. The dummy policy hides this because its chunk is just a slow ease. `docs/10_MODEL_AND_A100_PLAN.md` says the client "keeps executing the current chunk and requests the next one asynchronously" and sends "sub-sampled or interpolated chunk steps". The code is synchronous: `client.act` blocks the loop, with a 5 s timeout, while the arm holds its last goal. The doc and code disagree, and the replay speed will not match training. Also, the per-tick clamp of 0.05 in `run_loop` sits on top of the Guard's 0.35 step limit, so fast demonstrated motions will lag the target.

The half-chunk refetch discards the second half of every chunk. The reason is not explained, and ACT's temporal ensembling is not used.

## Server exposure and auth

`create_app` reads the token from the environment. If it is empty, `auth` does nothing. `main` binds `0.0.0.0` by default and `server/README.md` and `run.sh` mark the token as optional. `/health` and `/metrics` are never authenticated, which leaks model name, device and latency to anyone on the network. The client sends `Authorization: Bearer` over `http://`. The Docker image runs as root and has no healthcheck, which is minor.

The server also never sets `reset=True` from the client (`PolicyClient.act` has no parameter for it and `run_loop` never calls `client.reset()`). For ACT's `predict_action_chunk` this is harmless. For a stateful policy such as one with temporal ensembling or an internal action queue, episodes would leak state into each other (possible, depends on the checkpoint).

## Real LeRobot adapter assumptions

`LeRobotPolicy` has never run. The assumptions that will break it first:

- The image key is fixed at `observation.images.table`. This matches `record_demo.py`, but the plan itself says SmolVLA needs a rename to `camera1`. Nothing in the server applies a rename map.
- Outputs are clamped to 0..1 after `self.post`. If training used LeRobot's mean/std normalisation, the postprocessor un-normalises back to dataset units, which is only 0..1 if the dataset was recorded as norms. This is worth one assertion against the dataset stats at load time.
- Action width is sliced to 8 with no check.
- A vision policy called with no image fails inside `self.pre` and returns a 500.
- State is not checked for NaN or Inf. Torch's `clamp` passes NaN through, and `Guard.move` compares against it without rejecting it (possible, would need a NaN state from the backend).

## Test coverage

`scripts/test_policy_client.py` runs the dummy server, the sim backend and the Guard end to end, checks that an unreachable server raises `PolicyError`, and checks that station mode without the flag exits nonzero. Not tested: the auth path (the test removes `POLICY_API_TOKEN` from the environment), the real adapter, the Docker build, `bench.py`, chunk playback speed, e-stop on mid-run server failure, and `--backend station`. Two of the five checks cannot fail, as listed in the issues.

## Plan document

`docs/10_MODEL_AND_A100_PLAN.md` labels latency numbers as estimates and lists the elbow joint 3/4 hardware fault and the leader/follower j4 mismatch as risks before recording demos. There is no training script or checkpoint in this change, so the server has no model to serve yet.
