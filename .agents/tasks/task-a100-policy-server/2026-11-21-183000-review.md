# A100 policy server and robot-side client (v2)

Second pass over the FastAPI policy server, HTTP client and `scripts/run_policy.py`. Commit 80da922 addresses all seven v1 issues: chunk playback now runs in real time from `chunk_dt`, auth is required by default and covers every endpoint, the server binds `127.0.0.1` unless told otherwise, the checkpoint is validated at load, a missing image or NaN state returns 422, `client.reset()` runs at episode start, and the dry-run test now checks the 401 paths, playback rate and the 422 cases. The real LeRobot 0.4.4 path, the Docker image and the real arm are still unrun, and no trained checkpoint exists.

Watch for: (1) the checkpoint validation and action-range guard have no test, because the test only drives `DummyPolicy` (confirmed); (2) `--hz` above 10 makes playback faster than real time, because Guard caps the tick rate at 10 Hz while chunk advance assumes `--hz` (confirmed); (3) a non-ASCII `Authorization` header gives a 500 instead of a 401 (likely).

**Verdict**: APPROVED

## High-level view

Playback is now time-based. Each tick advances the chunk by `1/(hz*chunk_dt)` rows with linear interpolation, and the next chunk is fetched synchronously once half the chunk is consumed. The 30 fps ACT rows play back at real speed, and the new test asserts the fetch count for 30 fps and 100 fps chunks.

Security is now closed by default. Startup fails without `POLICY_API_TOKEN` unless `--dummy` or `--no-auth` is passed, `/health` and `/metrics` need the token, and the README says the token is cleartext and prescribes an SSH tunnel, VPN or TLS proxy. The Docker image still binds `0.0.0.0` inside the container, and the README tells operators to publish the port on `127.0.0.1`.

The real-model adapter reads the camera key from the checkpoint config and rejects wrong state or action shapes at load and out-of-range actions per request. None of that code has run, and the README says so.

## Playback clock versus Guard clock

`run_loop` takes the loop rate `hz` as the tick length and advances the chunk position by `1/(hz*chunk_dt)` rows. Guard separately paces `move` calls to `max_cmd_hz`, sleeping to enforce it. The loop lowers Guard's limit to `hz` when `hz` is smaller, but never raises it. With the default 10 Hz the two agree. With `--hz 20` Guard still ticks at 10 Hz while the chunk advances 6.7 rows per tick, so a 30 fps policy runs at 2x. The synchronous `client.act` call also adds wall time that the position counter does not see, so each refetch pauses the arm for the round trip (about 5 s worst case from the client timeout) while the chunk clock stays put. That is acceptable at A100 latencies and matches the plan's estimates, but the timeout is long for a physical arm holding its last goal.

## Checkpoint validation and the action range guard

Out-of-range actions raise per request, not at load. The `RuntimeError` becomes a 500, the client turns it into `PolicyError`, and `run_policy` e-stops, so the failure is fail-closed. Only the dummy server is exercised in `scripts/test_policy_client.py`, and the 422 tests use `VisionDummy` rather than `LeRobotPolicy`, so the config validation and range checks have no coverage. `get_policy_class`, `make_pre_post_processors(... preprocessor_overrides=...)` and `predict_action_chunk` are LeRobot 0.4.4 API calls that were written from docs, not run, so the first A100 load is the real test. Also, `--image-key` is silently ignored when the checkpoint has no camera input.

## Auth and exposure

`--no-auth` on a `0.0.0.0` bind is an explicit opt-in and is not tested. The header comparison uses `hmac.compare_digest` on `str`, which raises for non-ASCII input, so a crafted header produces a 500 instead of a 401. Requests are still rejected, so this is not a bypass.
